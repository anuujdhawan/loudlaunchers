## Second pass — accessibility and contrast of the new components

### Bug 3: collapsed menus left invisible controls in the tab order

Both header collapses used `max-h-0` + `opacity-0` with `overflow-hidden`, which
hides content **visually** but leaves it fully focusable and exposed to screen
readers. Measured before fixing:

| Container | State | Focusable descendants |
|---|---|---|
| `UtilityBar` (desktop, scrolled) | `height: 1px`, `opacity: 0` | **6 of 6** — email, phone, 4 socials |
| `#mobile-menu` (phone, closed) | `height: 0`, `opacity: 0` | **20 of 20** |

Keyboard focus therefore jumped to controls the user could not see — WCAG 2.4.3
(Focus Order) and 2.4.7 (Focus Visible) — and a screen reader announced the
mobile nav twice. Fixed by adding `inert={collapsed || undefined}` to the utility
bar and `inert={!open || undefined}` to `#mobile-menu` in `Header.jsx`. Verified
both directions: collapsed → not focusable, expanded → focusable, and the drawer
CTA still opens the lead modal. `inert` does not affect either collapse
transition. ESLint clean; React 19 accepts `inert` as a boolean.

Two other `max-h-0` containers (the mega-menu's expandable groups) were already
correct — 0 of 7 focusable, because their ancestor is `pointer-events-none`.

**Generalise this:** any `max-h-0` / `h-0` collapse needs `inert` (or
`aria-hidden` + `tabindex="-1"`). Grep `max-h-0` after building a nav.

## Third pass — the chat panel was modal on phones but not declared as one

### Bug 4: focus escaped the full-screen chat panel

`GuidedChat` declares `role="dialog"`, but had **no focus trap and no
`aria-modal`** — unlike `LeadModal`, which does both. On phones the panel covers
the whole viewport and locks body scroll, so it *behaves* as a modal while being
declared as a non-modal dialog. Measured with a `focusin` logger plus 14 real
`Tab` presses at 390×844:

```
  8. [IN ] BUTTON  Continue
  9. [OUT] BUTTON  Close the guided chat   ← the launcher bubble behind it
 10. [OUT] A       Skip to content
 11. [OUT] A       Loud Launchers home
 12. [OUT] BUTTON  Open navigation
 13. [OUT] A       Websites…               ← mega-menu link
```

Focus walked onto controls the user could not see — the same defect class as the
collapsed menus, and a WCAG 2.4.3 / 2.4.7 failure.

Fixed by making the panel's modality follow the breakpoint it already used for
scroll locking, so the two can't drift apart:

- Added `PHONE_QUERY = "(max-width: 639px)"` plus a `useSyncExternalStore`
  subscription (`subscribePhoneQuery` / `getPhoneSnapshot` /
  `getPhoneServerSnapshot`). Deliberately **not** `useState` + `useEffect` —
  that trips `react-hooks/set-state-in-effect`, and `useSyncExternalStore`
  avoids the extra commit entirely. Server snapshot is `false`, matching the
  desktop-first markup.
- Scroll-lock effect now keys on `isPhone` instead of reading `matchMedia`
  inline.
- New `Tab` trap, active only when `open && isPhone`, cycling within
  `panelRef` (same node-filter and first/last logic as `LeadModal.trapFocus`).
- `aria-modal={isPhone || undefined}` on the panel.

Desktop is intentionally left non-modal: the page stays scrollable and usable
while the chat is open, so focus must be free to leave. Verified after the fix:
**0 of 14** focus escapes on mobile, and on desktop `aria-modal` is absent
(`ariaModal: null`) with `body.style.overflow` untouched.

### The generalisable rule
A panel that fills the viewport on one breakpoint and floats on another has to
switch modality too. Tie the scroll lock, the focus trap and `aria-modal` to the
**same** media query, or they drift and you get a screen that looks modal but
isn't. Verify by counting focus escapes with a `focusin` listener, not by
eyeballing it.

## Six long-form service pages + the dropdown regression

Two requests: (1) the dropdown "doesn't go away when the cursor is on top — it has
to go *below* the dropdown to make it disappear"; (2) a separate, deeply

### The dropdown: the previous fix was one level too high

The note above called the shared-ancestor fix "structurally sound". It was not —
it was **scoped too wide**, and that is what produced this bug.

Root cause, found by probing rather than reasoning: `onMouseLeave={releaseMega}`
sat on the header **row** wrapper. That wrapper also contains the logo, the three
sibling nav links and the CTA, so leaving the trigger for any of them was *not*
leaving the ancestor → no close was scheduled. Only travelling *below* the panel
left the wrapper. Exactly the user's description.

Probe method that found it: open the menu, `mouse move` to each destination, then
read `document.getElementById("services-menu").hasAttribute("inert")`.
Siblings / logo / CTA → `OPEN <-- stays`; below the panel → `CLOSED`.

Fix: move the handler down to the per-item `div.relative` (trigger + panel only)
and give the panel its own `onMouseLeave`; the two halves own the close together.
The 22px trigger→panel gap is now spanned by a `::before` strip on the panel
(`before:-top-7 before:h-7`) instead of a DOM node — hovering a pseudo-element
counts as hovering its host.

Re-verified: siblings → CLOSED, logo → CLOSED, CTA → CLOSED, trigger edge → OPEN,
diagonal descent → survives, link click → `/services/search-engine-optimization`.

**Generalisable rule:** the close handler's host must contain the trigger and its
panel **and nothing else**. "Nearest common ancestor" is the right instinct but
easy to apply one level too high.

### ⚠️ The contrast auditor was lying, and the skill was the reason

The auditor reported **82 failures that were impossible** — near-white
`lab(90.68…)` text on a dark card scoring 1.35:1.

First hypothesis (wrong): alpha was being dropped from `oklab(… / 0.03)`. I
rewrote the parser to composite the full ancestor chain and got **byte-identical
output**, which proved the fix had not taken effect — a useful signal in itself.

Real cause, found by direct probe: **`canvas.fillStyle` does not resolve `lab()`
in this Chromium — it echoes the string back.**

```
canvasEcho: "lab(90.6853 0.399232 -1.45452)"   // input returned unchanged
```

The sentinel-magenta guard never fired, because the assignment was *accepted*, not
rejected. Reading L/a/b as R/G/B gave a near-black, hence the phantom 1.35:1.

**This invalidates a claim that was written into the skill** ("verified working in
this sandbox's Chromium for `lab()`, `oklab()` and `oklch()`") — that probe
happened to use a value canvas could handle. The skill has been corrected to say
canvas does **not** normalise these functions and that explicit conversion is
required, and the shipped `references/contrast-audit.js` now carries a
**self-test** that runs before any measurement and refuses to report if the
converter does not reproduce `lab(55.8958 81.2562 17.0278)` → `#ff176e`, white on
black → 21.00, white on `#ff176e` → 3.75, `#050507` on `#ff176e` → 5.43.

That self-test immediately earned its keep: when I hand-retyped the converter to
double-check the constants, my version returned `rgb(255,21,100)` for the brand
pink and `rgb(255,254,232)` for `lab(100 0 0)`. The shipped file's constants are
correct; a hand-typed "equivalent" is not. **Never trust a converter you have not
run the known-value test through.**

Corrected audit: **184 checks, 0 failures, 2 gradient cases flagged for manual
review.**

### The bigger find: `<br />` was jamming words together

While verifying the CTA I noticed the new H2's `textContent` read
`"Ready to move onSEO?"`. That is not a styling nit — it is what most naive scrapers,
LLM/answer-engine extractors and accessible-name computation actually read. The
browser hides it: `innerText` inserts a break, so it *looked* correct in every
screenshot and in my earlier tag-stripping audit (which replaced tags with a space,
masking the bug).

Cause: **JSX strips whitespace adjacent to a newline**, so

```jsx
Text
<br />
more text
```

produces text nodes `"Text"`, `<br>`, `"more text"` — no space anywhere. `textContent`
concatenates them to `"Textmore text"`.

Scale: **38 `<br />` across 12 files**, every one inside a heading or display heading.
Worst offender was the homepage H1 — `"Think it.Build it.Launch it."`.

Fix: insert an explicit `{" "}` after each break (`<br />{" "}`). It is an expression,
so JSX preserves it; a space at a line start is collapsed by CSS, so rendering is
byte-identical (verified against the hero screenshot). Applied with an idempotent
Node codemod; ESLint clean afterwards.

Verified with the authoritative test — comparing `textContent` against `innerText`
case-insensitively on every `h1/h2/h3`: **match on every heading on every page
tested.** (My first regex heuristic `[a-z0-9][A-Z]` threw 4 false positives — "B2B",
"ChatGPT" — which the innerText comparison correctly cleared. Prefer the comparison
over the heuristic.)

## Making the three dock bubbles look 3D

Request: "make all those 3 bubble icons a bit stylish 3d and professional."

### One recipe, three palettes

Resisted the obvious approach — hand-writing a `shadow-[…]` + `bg-gradient-*` chain per bubble.
Three hand-tuned chains drift apart, and their hover states end up disagreeing. Instead put a
single `.bubble-3d` recipe in `globals.css` and let each bubble supply only `--bubble-top`,
`--bubble`, `--bubble-deep`, `--bubble-glow` via a modifier class
(`bubble-3d--whatsapp` / `--chat` / `--call`).

The recipe composites four things, and all four are load-bearing:

1. a **radial sheen** offset above centre — `radial-gradient(115% 115% at 50% -12%, …)`
2. a **vertical ramp** to a deeper stop at 100%
3. an **inset rim + inner bottom shade** (`inset 0 0 0 1px` white, `inset 0 -5px 9px -3px` black)
4. **two** outer shadows — a tight contact shadow plus a wide tinted glow

Any one alone reads as a flat circle with a drop shadow. The inline `shadow-[…]`, `transition` and
`hover:-translate-y-0.5` utilities were then **deleted** from `FloatingDock.jsx` — the recipe owns
them now, so the three bubbles cannot diverge.

Motion: hover `translateY(-2px)` + stronger rim/glow over 220ms `cubic-bezier(0.22,1,0.36,1)`;
`:active` `translateY(1px) scale(0.955)`; glyph lift via `.bubble-3d svg { filter: drop-shadow(…) }`.
A `prefers-reduced-motion` block sets `transition: none; transform: none;` on the family.

### ⚠️ Pre-existing bug found on the way: focus turned the circles into squares

`globals.css` had a project-wide `:focus-visible { border-radius: 0.5rem }`. On keyboard focus
every `rounded-full` control snapped from `1.67772e+07px` to `8px` — the circle became an 8px
rounded square precisely when the user needed to see it. Invisible to mouse testing and to every
screenshot; only a real `Tab` press shows it.

Removed the `border-radius` from the rule. The focus ring still renders — browsers have traced the
outline around the element's own corners since Chrome 94 / Firefox 88 / Safari 16.4, so the
declaration was both unnecessary and harmful. A comment in the file records why it must not come
back.

### ⚠️ Methodological trap: the bubble's bottom edge is the wrong place to sample contrast

First pixel-sampling pass reported **2.88:1 FAIL** on a bubble. That number is real but
meaningless — it was sampled at the extreme bottom edge of the gradient, where **no glyph pixel
sits**. The icon is centred and ends ~13px above the edge.

Re-sampled a band around the glyph (`centre ±13px`), with the extreme edge reported separately as
information only:

| Bubble | centre | worst in glyph band | extreme base edge |
|---|---|---|---|
| WhatsApp | 10.38:1 | **7.65:1** | 5.99:1 |
| chat | 5.66:1 | **4.35:1** | 3.49:1 |
| call | 5.61:1 | **4.19:1** | 3.32:1 |

Worst glyph contrast **4.19:1** — all clear the 3:1 non-text bar, WhatsApp clears 4.5:1 outright.
`--bubble-deep` was raised to `#12a850` / `#cc0055` / `#8d2ce8` to get there. Sampling the edge
would have sent me chasing a non-problem.

### Verified

- Hover: `{"hovered":true,"transform":"matrix(1, 0, 0, 1, 0, -2)","transitions":"transform,
  box-shadow","duration":"0.22s, 0.22s"}`.
- Reduced motion: `{"reducedMotion":true,"transitionProperty":"none","transitionDuration":"0s"}`.
- Full-page contrast audits: `/` 296 checks / **0 failures**; SEO service page 431 / 0; `/about`
  251 / 0.
- ESLint clean (0 errors, 0 warnings). Zoomed crops reviewed at mobile / tablet / desktop — the
  call bubble correctly absent at desktop.

## Top-bar email/phone were unclickable; navbar phone pill removed

Request: "remove the phone number from the navbar and make the email address and phone

should take to calling app."

### ⚠️ The links already had the right `href`s — they just could not be clicked

`<header>` sets `pointer-events-none` so its transparent areas do not swallow clicks meant
for the hero. Every interactive subtree therefore has to opt back in, and the **utility bar
was the only one that never did**:

| Element | `pointer-events` |
|---|---|
| nav row | `auto` (explicit) |
| mobile drawer | `auto` (explicit) |
| **utility bar** | **inherited `none`** |

Measured, not reasoned — hit-testing each link's centre:

```
mailto:anoojdhawan@gmail.com  y=14  pe=none  hit → SECTION (the hero)
tel:+919468055396             y=14  pe=none  hit → SECTION (the hero)
navbar phone pill             y=66  pe=auto  hit → itself
```

So a click passed straight through both links into the page beneath. The fix is
`pointer-events-auto` on the bar's outer div, with a comment naming the `<header>` rule as
the reason it is load-bearing.

**Generalisable rule: a `pointer-events-none` ancestor is a per-subtree opt-in.** When you
add any interactive element inside one, grep the sibling subtrees for the `auto` and match
it. A mouse test that "looks fine" proves nothing here — the control renders normally and
simply never receives the event. Verify with `elementFromPoint` at the control's centre and
assert the hit is the control or a descendant.

Regression-checked the collapse: with `pointer-events-auto` now on the bar, scrolled to
400px it is `height: 1px` (just the border), `inert`, and a point at y=14 hits the **nav
row**, not the bar. The `max-h-0` collapse still protects the band.

- **Navbar phone pill deleted.** The nav row now reads

  with no `tel:` link in it (asserted, not eyeballed). The number is still reachable from
  the top bar, the mobile drawer's contact block, the dock's call bubble and the footer.
- **New helpers in `src/lib/site.js`**, alongside the existing `whatsappLink`:

## The 3D treatment extended to every button on the site

Request: "same treatment you did to bubble icons to make them look professional and 3d
we need that to be done to each and every button of the website."

### One recipe, five palettes, two amplitudes

`globals.css` gained a `.btn-3d` family built from the same four ingredients as
`.bubble-3d` — top gloss, vertical light→base→deep ramp, inset rim plus inner bottom shade,
and a two-part outer shadow (tight contact + wide tinted glow). The two families share a
language on purpose so the dock and the buttons read as lit by the same lamp.

One deliberate difference: a button is wide, so its gloss is a **linear** ramp, not a radial
sheen. A radial highlight on a 200px pill reads as a bulge rather than a surface.

Amplitude is a variable, not a second recipe. `.btn-3d--soft` lowers the numbers for icon
buttons and chips, because a 40px control carrying a 34px shadow reads as a sticker.

Palettes: `--pink`, `--white`, `--ink` (dark glass), `--outline`, `--ghost`, plus `--flat`
for inert controls and `--reveal` for controls that animate their own visibility.

**Every ramp stop is a contrast decision.** `--btn-top`, `--btn` and `--btn-deep` are all
surfaces the label can sit on, so all three clear AA against their ink: the pink ramp is
6.45 / 5.43 / 4.56:1 for the dark `#050507` label. An earlier candidate for the deep stop,
`#d90f61`, measured 4.06:1 and was rejected. The hover ramp is verified too (7.65 / 6.08 /
4.83:1).

Because the recipe reads custom properties, the white button's hover-to-pink is a **palette
swap** rather than a second shadow chain — every depth cue survives it for free.

### Reached through one component where possible

`Button.jsx` covers ~22 call sites; its variants now just name a palette, and the utilities
the recipe owns (`shadow-2xl`, `hover:-translate-y-0.5`, `transition`) were **deleted** so
nothing double-applies. That is the same rule as the bubbles: one owner per property.

The remaining ~30 ad-hoc buttons were done individually — header CTA, mega-menu CTA, drawer
CTA and its group toggles, hamburger, hero replay, footer socials, newsletter submit, chat
send/edit/close, lead modal chips/submit/close, contact chips/submit, back-to-top, pagination,
the four white page CTAs, the skip link, and the filter chips.

**Deliberately not treated:** static badges and tags (a `rounded-full border px-*` span with
no hover state is a label, not a button), nav list rows, the mega-menu service cards, form
inputs, and decorative HUD panels. Applying depth to those would make every label look
clickable.

### ⚠️ The contrast auditor had a bug that hid every button

The first audit after this change reported 7–13 failures per page, all at ~1:1 — dark ink on
`rgb(5,5,7)`. They were false.

Cause: the auditor flattened `background-image` into one stop list. A depth recipe is a
**layer list** — a translucent gloss layered over an opaque ramp — so flattening yields
translucent stops, `opaqueGradient` evaluates false, and the "the gradient never painted"
branch survives, testing dark text against the page background.

Fixed by compositing the layers bottom-up (`imageLayers` + `layerStops`), because a
translucent layer over an opaque one still paints opaque. It also now returns `null` rather
than `[]` when nothing parses — an empty array makes `.every()` vacuously true and would mark
the element wrongly opaque.

After the fix: **0 failures** on `/` (293), `/services` (244), `/work` (315), `/about` (239),
`/contact` (181), the three detail pages (442 / 200 / 273), and mobile at 390×844 (296 / 256 /
193 / 263). One remaining flag, `/blog`'s "Prev" at 1.95:1, is the **inactive** pager arrow —
asserted as `aria-disabled="true"`, `tabIndex="-1"`, `pointer-events: none` — which WCAG 1.4.3
exempts.

### ⚠️ Tailwind v4 emits `translate` / `rotate` / `scale` as standalone properties

Found while adding the back-to-top reveal. Tailwind v4 does **not** compile `translate-y-4`
to `transform: translateY(...)`; it sets the standalone `translate` property. Measured:

```
skip link (has -translate-y-24):  translate: 0px -96px   transform: none
Tailwind `transition` property list: "... transform, translate, scale, rotate, filter ..."
```

Two consequences, both of which I had wrong at first:

1. **My `--reveal` modifier was missing `translate`.** It listed `transform` and `opacity`, so
   the slide would have snapped while only the fade eased. Now verified animating both:
   `translate: 0px 16px → 0px`, `opacity: 0 → 1`, over 0.32s.
2. **A code comment I wrote was wrong.** I had claimed `group-hover:rotate-45` would collide
   with `.btn-3d:hover`'s `transform` because the unlayered recipe wins. It would not — `rotate`
   is a separate property and the two compose. The MethodAccordion restructure is harmless
   (the disc is radially symmetric, so it looks identical either way) but the comment is
   corrected, and it is a good reminder that a plausible cascade story is not evidence.

### Hover-test harness: five separate false negatives

Getting a trustworthy hover measurement took longer than the change did. Each of these
reported "lift=NO" and looked like a recipe failure:

| Trap | What it actually was |
|---|---|
| `querySelector('.btn-3d--white')` | matched the **skip link**, parked at `translate:0 -96px` — off-screen, unreachable |
| `querySelector('.btn-3d--ink')` | matched the **hamburger**, `display: none` above `lg` |
| ancestor walk for `pointer-events: none` | rejected everything in the header — `pointer-events` is **inherited**, so the computed value on the element is already authoritative. `<header>` sets `none` and the utility bar re-enables it deeper in |
| in-viewport filter | rejected below-the-fold buttons *before* scrolling to them — chicken-and-egg |
| `opacity < 0.5` filter | rejected elements still mid-`Reveal` |

Also: `hover <sel>` on a closed mega-menu CTA does nothing, because the panel is
`pointer-events: none` — on screen, measured, and genuinely unreachable. And moving the pointer
to coordinates it already occupies dispatches no `mousemove`, so the "before" reading is stale.

Final method that worked: pick the first *reachable* candidate (computed `pointerEvents` on the
element, exclude off-screen `position: fixed`), `scrollintoview`, wait ~1.4s for the reveal to
settle, park the pointer at 5,5, read, then `mouse move` to the element's centre.
