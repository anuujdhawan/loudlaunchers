## "Where we launch": India → Europe

User asked to remove India from the region list and add Europe.

`src/lib/site.js` — `areasServed` swapped `"India"` → `"Europe"` **in place** (position 6 of 7),
because the list is ordered by client volume rather than alphabetically and an in-place swap
changes exactly one chip in the row the user was looking at. Added a comment recording that

**The non-obvious part — `areasServed` was not purely display data.** It feeds `areaServed` in
JSON-LD, and all four schema consumers inlined
`{ "@type": "Country", name }`. That was true only while every entry was a country; Europe is a
continent, and schema.org defines no `Continent` type, so shipping it would have put a
machine-readable falsehood on six page types (133 `areaServed` nodes total).

Fixed by adding `areasServedSchema()` to `site.js` with a small `AREA_SCHEMA_TYPE` exception map
(`{ Europe: "Place" }`), and routing all four call sites through it:

- `src/app/layout.js` — two blocks (Organization `areaServed`, and the nested one inside
  `contactPoint`); both were identical apart from indentation
- `src/app/services/page.js` — `ItemList` of `Service` nodes
- `src/app/services/[slug]/page.js` — `Service` node

The three text renderers (`about/page.js`, `contact/page.js`, `Footer.jsx`) and the two
`llms.txt` joins needed no change — they print the strings.

Also updated the region list inside the shared FAQ answer ("…UAE, India and Singapore" →
"…UAE, Europe and Singapore"), which would otherwise have contradicted the chip row on the two
pages that render the FAQ.

**Deliberately left alone:** `src/lib/countries.js` still contains India. That is the ~190-entry
dial-code picker for the lead form, not a service claim — removing it would break the selector
for Indian visitors, and `+91` is the studio's own country code.

Verified: `Europe` present and `India` absent on `/`, `/about`, `/contact`, `/services`, `/work`,

## Favicon built from the brand mark + WebP pass

User: "keep the main LL logo part as favicon … convert the image file in the required width and
height" and "use every image in the website as webp format".

**Favicon.** Source is `public/logo-mark.webp` (560×500, has alpha) — the mark alone, not
`logo.png`, which is the full lockup on an opaque white background. Sampled its colours first:
**half brand-pink (`#ff3080`-ish), half near-white (`#f0f0f0`)**. That decided the design — a bare
transparent mark would lose its white half against Google's white SERP and light browser chrome,
so the mark is composited onto a **brand-dark tile** (`#14141c → #050508`, taken from
`globals.css`), which makes its appearance deterministic on any background. Mark sized to **80%**
of the tile (compared 74% vs 80% side by side; 80% is markedly more legible at 32px).

Generated, all square: `src/app/favicon.ico` (hand-built ICO containing 16/32/48 PNGs — no ICO
writer was available, and PNG-in-ICO is universally supported), `src/app/icon.png` (192 = 4×48,
satisfying both Google's old "multiple of 48" wording and the current "larger than 48×48"
recommendation), `src/app/apple-icon.png` (180), `public/icon-512.png`, and
`public/icon-maskable-512.png` (mark at 56% for the maskable safe zone).

Google's current spec, confirmed rather than assumed: square 1:1, ≥8×8, **strongly recommend
larger than 48×48**.

**Manifest was wrong** — it declared `logo-mark.webp` with `sizes: "any"`, but that file is
560×500, so an OS scaling it into a square slot would distort it. Now points at the square tiles
plus a `purpose: "maskable"` variant.

**WebP.** The displayed images (`logo-mark.webp`, `logo-full.webp`) were **already WebP**, so the
only genuine conversion was `logo.png` → `logo.webp` (53KB → 6KB, 512×482), referenced by the
Organization schema. **The OG images deliberately stay PNG**: they are consumed by social
crawlers, never by a page visitor, so they cost nothing in page weight — and LinkedIn does not
render WebP previews at all, so converting them would silently break every LinkedIn share.

**But they were badly optimised, and that was worth fixing.** sharp's PNG `effort` defaults low;
`effort: 10` takes the same 1200×630 cards from ~175KB to ~94KB, **46% smaller, lossless, same
format**. Fixed in the generator (`scripts/generate-og-images.mjs`, now a shared `PNG_OPTS`
const), then regenerated: **3.51MB → 1.84MB** across 21 cards, LinkedIn-safe.

**Deliberately not converted:** the five unused create-next-app SVGs in `public/`
(`file`, `globe`, `next`, `vercel`, `window`) — vector, referenced in zero files, and one is
Vercel's logo. Rasterising them to WebP would be a downgrade. Offered deletion instead.
`logo.png` is now unreferenced; kept as the designer's master rather than deleted.

**sharp gotcha hit and fixed:** chaining `.composite(...).resize(...)` in ONE pipeline fails with
"Image to composite must have same dimensions or smaller", because sharp applies `resize` to the
base image *before* compositing. Composite at master size into a buffer, then resize that.

Verified: icon links in the live DOM (`icon 48x48 /favicon.ico`, `icon 192x192 /icon.png`,
`apple-touch-icon 180x180 /apple-icon.png`), all icon URLs 200 with correct content types, schema
logo now `/logo.webp`, all 21 OG cards still 1200×630 and pixel-identical, all routes 200,
ESLint exit 0. Artifacts: `favicon-sizes-16-to-192.png`,
`favicon-in-browser-tab-light-dark.png`, `favicon-standard-vs-maskable.png`,
`og-card-after-optimisation.png`.
