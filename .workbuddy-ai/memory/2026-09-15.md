# 2026-09-15

## Premium redesign + blog platform (loud-launchers-website)

Request: make the site look professional/premium/modern while keeping the existing theme and
hero animation; make navbar + footer stand out; add more pages; add a blog section with 20
unique posts backed by keyword/trend research; list Blog in the navbar; blogs page with a left
category panel, "All" + per-category views, pagination, cards, and a detail page per post.

### Architecture decisions
- **Blog data layer: `src/lib/blog.js`** replaces the old `src/lib/posts.js`. Single source of
  truth: a `categories` registry (9 entries) + 20 posts. Adding a category is a one-line change
  and it automatically propagates to the sidebar filters, mobile chip rail, footer Insights
  column, sitemap, `llms.txt` and the blog index. This is what satisfies "categories can be
  increased afterwards".
- **URL-driven state** for blog filtering/pagination (`searchParams`), not React state. Makes
  filtered views shareable, crawlable and functional without JS. Helpers: `blogHref()`,
  `paginate()` (clamps out-of-range pages).
- **Cover art is generated SVG, not stock photos** (`PostCover.jsx`): 5 composition variants
  selected by `(post.cover - 1) % 5` × per-category accent. Zero image bytes, every post unique.
  Each slug gets its own gradient/pattern ids to avoid SVG id collisions.
- **`llms.txt` is a route handler** (`src/app/llms.txt/route.js`, `dynamic = "force-static"`)
  generated from the same registries so it can never drift from the content.
- **OG images generated at build time** by `scripts/generate-og-images.mjs` (sharp rasterizes
  SVG → PNG). Run via `npm run og`. Outputs `public/og.png` + `public/blog/og/<slug>.png`.

### Next.js 16 gotchas hit (repo warns "This is NOT the Next.js you know")
- `params` / `searchParams` are **Promises** — must be awaited.
- `priority` on `next/image` is **deprecated**. Use `loading="eager" fetchPriority="high"`.
  Do NOT put `fetchPriority` on inline `<svg>` — causes a hydration mismatch.
- React Compiler's `react-hooks/set-state-in-effect` rule **errors** on setState in an effect
  body. Route-change menu resets in `Header.jsx` use the render-time state-adjustment pattern
  (`renderedPath` guard) instead.

### Bugs found and fixed
- `getCategory is not defined` → 500 on `/blog?category=*`. Build passed because `/blog` is
  dynamic; only the filtered request crashed. Lesson: smoke-test dynamic filter URLs, not just
  the build.
- Footer oversized wordmark clipped at viewport edges → replaced clamp() text with an SVG using
  `textLength="996" lengthAdjust="spacing"` so it scales exactly to the container.
- `PostCard` meta row wrapped at 3-col width → added `shortReadingTime()` / `formatShortDate()`
  helpers + `whitespace-nowrap`.

### Robustness improvement
- `Reveal.jsx` starts at `opacity-0` and relies on IntersectionObserver, so a no-JS visitor saw
  a blank page. Added `data-reveal` to the wrapper and a `<noscript>` style override in
  `layout.js` (via `dangerouslySetInnerHTML`, the React-safe form) forcing opacity 1.

## Blog content audit → fixed a serious thin-content problem

Ran an SEO audit against the user's stated goal ("rank on the internet SERP results") and found
the biggest blocker in the whole project: **19 of 20 posts were under 600 words** — average 533,
minimum 450, totalling 10,651 words. Several were targeting high-commercial-intent keywords
("how much does a business website cost in 2026") at 450 words, which will not rank against
agencies publishing 2,000-word guides.

**Before:** 20 posts, 10,651 words, avg 533w, min 450w, 2 FAQs each, ~4 sections each.
**After:** 20 posts, 29,102 words, avg 1,455w, min 1,347w, 4–6 FAQs, ~9 sections each.

Approach: expanded one post by hand
(`how-much-does-a-business-website-cost-in-2026`, 450 → 1,459w) to establish the target depth
and voice, then delegated the remaining 19 to a single general-purpose subagent with the
expanded post as its explicit style reference. One writer on one file — parallel agents would
have clobbered each other on `blog.js`.

**Rules given to the writer** (worth reusing for any content-expansion job):
- Frozen fields: `slug`, `title`, `description`, `category`, `tags`, `date`, `updated`,
  `featured`, `cover` must not change — they drive routing, metadata, sitemap and cover art.
- `answer` must stay 40–60 words (the answer-engine snippet block). Six were over and got
  trimmed.
- Section headings must be question-led — they double as the TOC and as answer-engine targets.
- Do **not** fabricate cited statistics. Reuse figures already in the post or use generic
  industry ranges. No invented "according to Gartner 2026".
- Voice: direct, specific, opinionated, no filler. "An app is not a project that finishes; it is
  a product with a monthly bill."

**Verified independently, not on the agent's word:** all 20 slugs still match the expected set
exactly (none missing, none added), covers still unique 1–20, categories valid, dates still ISO,
titles/descriptions still unique, every answer 40–60 words, every post ≥1,347 words. ESLint
clean, build green (45 routes).

**Follow-on:** `readingTime` changed, and `scripts/generate-og-images.mjs` renders readingTime
into the OG cards — so the 20 OG images were stale. Re-ran `npm run og`. **Remember: changing
any post metadata that the OG script reads means re-running `npm run og`.**

Also noticed but NOT fixed: the original `readingTime` values were inaccurate (450-word posts
claimed "7 min read"). Now correct at ~1,450 words.

## Technical SEO audit → fixed a site-wide social-card bug

Audited titles, descriptions, canonicals, h1 counts and JSON-LD across 10 page types.
**18 problems found, all now fixed.** The important one:

**8 of 10 page types had NO `og:image`.** Next.js merges metadata **shallowly** — a page that
defines its own `openGraph` object *replaces* the layout's entirely, including `images`. Every
page that set `openGraph: { title, description, url }` without `images` silently shipped a
blank social card. Only the home page and blog posts were unaffected (they set `images`
themselves). This is invisible unless you fetch the rendered HTML and look for the tag.

Fix: created `src/lib/seo.js` with `og()` / `twitter()` builders that always attach the image,
plus `clamp()` and `BRAND_SUFFIX_LENGTH` / `TITLE_LIMIT` constants. All 9 metadata files now
build their social blocks through the helpers, so the bug cannot come back.

Other fixes:
- **Titles over 62 chars** (home 66, services 77, about 66, blog 65, case detail 82, service
  detail up to 67). The root layout appends `" | Loud Launchers"` (17 chars) via
  `title.template`. Added an `seoTitle` field to each service, shortened page titles, and for
  blog posts used `title: { absolute }` when `title + 17 > 62` so the brand suffix is dropped
  rather than the title being truncated. Verified both branches fire (2 posts keep the suffix,
  18 bypass it).
- **Meta descriptions over 160 chars** (home 248, case detail 281, service detail 181, services
  170, contact 167). Now clamped via `clamp()` — but note the home page clamps only the *meta
  tag*; `site.description` is left intact for the Organization JSON-LD and `llms.txt`, where a
  longer description is correct.

**Final state:** 16 pages audited — 0 missing og:image, 0 titles over 62, 0 descriptions out of
range, exactly one h1 per page, all JSON-LD parses, every page has a canonical and twitter:image.

Reusable lesson: `og:image` presence must be checked on the *rendered* HTML of every page type.
A layout-level `images` entry does not propagate to pages that define their own `openGraph`.

## WCAG contrast audit → 99 failures down to 4, all one root cause

Last accessibility item: colour contrast. Measured in a real browser, not by eye.

**Measurement method (the part that matters).** A canvas-based colour parser silently fails on
Tailwind v4 output: computed styles come back as `lab()` / `oklab()`, canvas keeps the previous
`fillStyle`, so every such element was reported as black. The first run claimed 175 impossible
failures, including 1.01:1 on plainly-visible text. Wrote an explicit conversion instead —
`lab()` is **D50**, so it needs a Bradford D50→D65 adaptation before the luminance formula;
`oklab()` is already D65. Corrected result: **99 real failures across 272 elements**.

**Measure surfaces, not just the page background.** Text sits on composited surfaces
(`bg-white/[0.02]`…`[0.07]` over `--color-ink` / `--color-panel`), and a gradient has no single
colour — so the audit expands each gradient into one candidate per colour stop and reports the
worst. The lightest surface in the system is `white/[0.07]` over `--color-panel` = `rgb(30,30,36)`.
That is the value every replacement had to clear — **not** `#050507`.

**Two culprits:** `text-zinc-500` (#71717a, 4.21:1) ×84 and `text-zinc-600` (#52525b, 2.63:1) ×27,
across 18 files. Both under the 4.5:1 AA floor.

**Fix — semantic tokens, not a find/replace.** Added to `@theme` in `globals.css`:
`--color-muted: #8b8b95` (6.04:1 on ink, 4.92:1 worst case) and `--color-subtle: #86868f`
(5.64:1 / 4.60:1), each documented in place with its measured numbers. Replaced 111 usages.
`#7c7c86` was rejected: it clears 4.5:1 on the page but fails at 4.01:1 on the lightest surface.

**Trap a blind sed would have broken:** `NewsletterForm.jsx` has a light variant on a white
background where `text-zinc-600` is *correct* (7.73:1) and `text-zinc-400` is *wrong* (2.56:1) —
the exact inverse of the dark surfaces. Handled that file by hand. (The light variant turned out
to be unused — the only call site is `<NewsletterForm />` in Footer — but it is now coherent.)

**Result:** 99 → 4. Swept 12 page types; **every remaining failure shares one root cause — white
text on the brand pink** (#ff176e = 3.75:1; gradient end #ff3d88 = 3.35:1). The sweep also caught
one the single-page audit had missed: the disabled `Prev` pager (`text-zinc-700`, 1.95:1) — exempt
under WCAG 1.4.3 as an inactive UI component, as are the 7 decorative `aria-hidden` `text-zinc-700`
separators.

**Key number for the pink decision:** black on `#ff176e` is **5.60:1**, and on `#ff3d88`
**6.28:1**. So the brand pink can stay byte-identical and still reach AA — only the label colour
changes. Left to the user, since "keep the same theme" was an explicit constraint.

**Tooling notes (each cost real time):**
- `agent-browser eval --stdin` accepts a piped script. Use it for anything non-trivial — it
  removes the shell-quoting/heredoc problems entirely.
- Starting the prod server as `(npx next start &)` inside a subshell **dies when the subshell
  exits**, producing 502s minutes later. Must run it as a persistent background task.
- `Reveal`'s `opacity-0` start would skew measurement, so the audit injects
  `[data-reveal]{opacity:1!important}` (same selector as the noscript fallback) and removes it after.

**Verified after the change:** ESLint exit 0; build green (45 routes); Tailwind emitted
`.text-muted` / `.text-subtle` and resolved the vars (`--color-muted:#8b8b95`); metadata re-checked
on 9 page types — 1 og:image, 1 twitter:image, 1 canonical each.

### Pink buttons resolved (user said "do whatever is best")

The only remaining AA failures were white text on the brand pink (3.75:1 solid, 3.35:1 on the
gradient end). Chose to **keep the pink byte-identical and move the labels to `#050507`** — black on
`#ff176e` is 5.60:1, on `#ff3d88` 6.28:1. Rationale: the explicit constraint was "keep the same
theme", and the site already uses `bg-white text-black` as its primary button, so dark-on-bright was
already the established language. Rejected darkening the accent to `#e8005c` (4.58:1) — a thin
margin *and* it alters the brand colour, which was the one thing to avoid.

Files touched: `Button.jsx` (primary + secondary hover), `Header.jsx` ×3 (desktop CTA, mobile CTA,
mobile-menu CTA hover), `NewsletterForm.jsx` (Subscribe), `Pagination.jsx` (current page),
`MethodAccordion.jsx` (active step), `contact/page.js` (submit), `layout.js` (`selection:`), plus the
five `bg-white … hover:bg-[#ff176e] hover:text-white` buttons (BlogSidebar, blog, work, services,
Header) where `hover:text-white` was simply dropped so the label stays dark through the hover.

Deliberately left alone: the hero's replay-icon circle (`HeroLaunch.jsx:286`) is white on pink at
3.75:1 — it is a **graphic**, the non-text threshold is 3:1, so it passes; the hero is also the one
thing the user asked not to disturb. The 7 decorative `aria-hidden` `text-zinc-700` separators are
exempt as pure decoration.

**Final: 0 failures on 11 of 12 page types.** The one remaining hit is `/blog`'s disabled `Prev`
pager (`text-zinc-700`, 1.95:1) — exempt under WCAG 1.4.3 as an inactive UI component.

**Auditor bug found and fixed — worth remembering:** `candidateBgs` kept a fallback candidate for
the element's own `background-color` alongside the gradient stops, i.e. a background the text never
sits on. With white text it scored *well*, so it never surfaced; after switching to dark text it
produced two phantom failures at 1.00:1 and 1.09:1 that looked exactly like a regression I had just
caused. Fixed by keeping that branch only when the gradient is partially transparent. **Lesson: when
a change makes previously-passing checks fail in a way that makes no sense, suspect the measurement
before the code.**

## Guided chat bot, WhatsApp redirect, lead modal, and the phone-number sweep

**Request:** two stacked bottom-right bubbles (guided chat + WhatsApp redirect), a scripted chat flow
collecting services / country of origin / country of residence / name / email / phone, a WhatsApp
redirect to **+91 9468055396** used everywhere on the site, and a compact lead-form modal opened by
every "Start a project" CTA.

**The phone number changed in one place.** `src/lib/site.js` holds `phone` (E.164 `+919468055396`,
used for `tel:` links and the Organization schema `telephone`) and `phoneDisplay`
(`+91 94680 55396`). Everything else derives: header utility bar, header CTA, mobile drawer, footer,
about, contact, JSON-LD and `llms.txt`. Added a `whatsapp` block (`919468055396` — no `+`, which is
what `wa.me` requires) plus a `whatsappLink(message)` helper. The old `+1-555-010-4400` is gone from
every page type, verified by grepping the built HTML.

**New files:**
- `src/lib/countries.js` — ~190 countries with ISO code + dial prefix, plus `resolveCountry()` and
  `searchCountries()` (prefix > word-boundary > substring > dial-code ranking).
- `src/lib/lead.js` — `LEAD_EVENT` / `openLead()` event bus, `CHAT_STEPS` (the conversation as data),
  `reviewRows()`, `composeLeadText()`, `submitLead()` (POST to `NEXT_PUBLIC_LEAD_ENDPOINT`, else a
  `mailto:` fallback — same pattern as NewsletterForm).
- `src/components/CountrySelect.jsx` — ARIA combobox with `direction="up" | "down"`.
- `src/components/PhoneInput.jsx` — dial picker + number, `composePhone()` / `splitPhone()`.
- `src/components/GuidedChat.jsx` — the bot. Control pinned in a `shrink-0` area below a `flex-1`
  scrollable transcript.
- `src/components/LeadModal.jsx`, `src/components/LeadTrigger.jsx`, `src/components/FloatingDock.jsx`.

**Decisions worth keeping:**
- **The transcript is derived, not stored.** `buildTranscript(stepIndex, values, editing)` recomputes
  the visible conversation from state. Appending to a message log from an effect tripped
  `react-hooks/set-state-in-effect` (React Compiler treats it as an error), and deriving it also makes
  "edit an earlier answer" rewrite history correctly for free.
- **The chat's control sits outside the scroll container.** An `absolute` dropdown inside
  `overflow-y-auto` is clipped by it; a `shrink-0` footer plus an upward-opening list fixes that and
  stops the input scrolling away. Both `CountrySelect` call sites use `direction="up"`.
- **WhatsApp bubble is `bg-[#25D366] text-[#050507]`** — white on that green measures only 1.98:1,
  dark measures 10.6:1. Recognisable *and* accessible, and consistent with the dark-on-bright CTA
  convention established in the earlier pink-button fix.
- **All 9 "Start a project" CTAs open the modal** (header ×3, services hero, service detail, about,
  work, CTA section, footer, blog sidebar). `Button` gained `opensLead` / `leadSource`; the blog
  sidebar uses `LeadTrigger` because it is a server component.
- The footer's company-links entry `{ href: "/contact", label: "Start a project" }` deliberately
  stays a real link — that one is navigation, not a CTA.

**Bugs found and fixed:**
- **Phantom horizontal scrollbar in the modal.** `overflow-y-auto` alone makes `overflow-x` compute to
  `auto`, so the decorative `-right-20 -top-20` glow produced a scrollbar. Fixed with an explicit
  `overflow-x-hidden`. Note that `scrollWidth > clientWidth` still reports `true` afterwards, so that
  comparison cannot detect it — check `getComputedStyle().overflowX`.
- **`BackToTop` was `fixed bottom-6 right-5`** and would have collided with the new bubbles. It now
  takes a `className` and is positioned by `FloatingDock`, which owns the whole corner.
- **agent-browser `click` does not auto-scroll**, and `scrollintoview` reported success without moving
  (`scrollY` stayed 0) — clicks then landed on the wrong coordinates. Scroll explicitly with
  `window.scrollTo({top, behavior: "instant"})` and assert `inView` first. Also: `:has-text()` and
  `text=` selectors are unsupported, and a click inside a `pointer-events-none` ancestor (the closed
  mega menu) silently no-ops rather than erroring.

**Verified:** ESLint exit 0; build green (45 routes); chat flow end-to-end including the
edit-from-review path; modal validation (5 alerts), submission, Escape and backdrop close; every CTA
entry point; residence → dial auto-fill (+971 from UAE, +49 from Germany); the WhatsApp handoff link
